# 数据质量规则

> 来源：data-model-builder (DMB) 探源六项 + rules-contract Q1-Q9 + sickn33 data-quality-frameworks
> 每次扫描探查时，跑 `scripts/probe_source.py` 自动出报告

## 探源六项必查

| # | 检查项 | 查什么 | 标记条件 | 报告里的样子 |
|---|---|---|---|---|
| ① | 行数/字段/主键 | 逐表基础信息 | — | table_name | rows | cols | pk |
| ② | 空值率（含空串） | 每个字段 NULL + '' 占比 | >10% 标粗、100% 标"可能无用" | col | null_rate | flag |
| ③ | 枚举全量 | DISTINCT 列出（排除日期/ID/唯一标识） | 自动排除日期类/唯一标识类 | col | distinct_values (top 20) |
| ④ | 完全重复行 | 所有列一模一样的行数 | >0 业务上"一件事"的边界在哪？问用户 | rows | duplicate_count |
| ⑤ | 时间范围 + 数据悬崖 | 按年统计行数 | 末年行数 < 前一年 50% → "年份未存满，趋势对须用同期口径" | year | count | cliff_flag |
| ⑥ | 孤儿外键 | xxx_id 猜父表 | 子表有父表没有的行数 | child_table.fk | parent_table | orphan_count |

**单表库的 ⑤⑥ 两项天然无对象，为空正常。**

## 空字符串 = 空值

> 验证来源于 DMB 案例 9 实测：真实脏数据常用空字符串 '' 而非 NULL。
> 探源时必同查 IS NULL 和 = ''，否则空值率报 0% 假阴性。

## 枚举含义靠数据推断后，必须向用户复述确认

> 来源 DMB case 5 实测发现：
> 用户答不上枚举含义（"不清楚你自己看着办"）时，AI 依数据证据推断的含义，**必须把推断明确复述给用户确认**。
> 禁止：自定含义后，再拿它当前提去问衍生问题（用户确认的是你的错误框架）。

## 质量检查流程（借鉴 sickn33 data-quality-frameworks）

```
发现脏数据 → 判断类型（缺失/枚举/格式/异常值）
  → AI 提出修复建议 → 用户确认
  → 记录到清洗日志（output/<case>/cleaning-log.md）
  → 在最终报告的"数据质量"章节体现
```

## 质量规则 Q1-Q9（借鉴 DMB rules-contract）

| # | 规则 | 说明 |
|---|---|---|
| Q1 | 以源表真实数据为准 | 探源时必看真实数据（SELECT 5~10 行），不只看表结构定义 |
| Q2 | 无主键 = 脏数据 | DWD 层拦截，不脏数据进统计 |
| Q3 | 枚举值看真实数据 | 用 SELECT DISTINCT 列出来，不等文档 |
| Q3a | 枚举含义推断后要用户确认 | 见上方规则 |
| Q4 | 空值率 >10% 标红 | 含空字符串，= '' |
| Q4a | 100% 空值标"可能无用" | 废弃字段/未启用/数据灌入有误 |
| Q5 | 口径卡走 4 步 | 口述→举例→沉淀→实现，不跳步 |
| Q6 | 公式合同统一 | 所有计算路径用同一套公式 |
| Q7 | 逐指标三层对账 | 口径卡现场算 vs 肉眼 vs 数值——三个数字一样算通过 |
| Q8 | 穷举对账 | 每个部门/维度值/指标/时间颗粒对一遍 |
| Q9 | 用户实测才算 | 自动化测试只是"代码层已验证" |
